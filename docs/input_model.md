# 一般化した入力（駅の点から線形を作るときに人が与えるもの）の構想

2026-11-08、ユーザーの構想（原文の要旨）。状態：**構想の記録。形（ファイルの決まり）と作り方は【未定】**。
目的：いまの入力（FreeTrain のセーブ、線形を表す作図の GeoJSON、運転系統を表す OuDia のダイヤ）に頼らず、駅の点と条件だけから
線形を作れるようにする。作図の GeoJSON があるのは択捉島・国後島だけで、ほかの路線（次は沖縄の架空鉄道。セーブとダイヤはあり、
GeoJSON はない）では、少なくとも下の入力が要る。最終的な目標②（路線選定）の入力でもある。

## 1. 原則
- **線路の規格が先、車両が後**。本来は路線の規格があって、そこに入れる車両が決まる。走っている車両から線形の条件を決めるのは逆
  （いまの計算は、系統の車両から勾配の上限を手で当てていて、気動車の系統が 33.3‰ の区間を走る不整合が起きた。`vertical_curve.md` 5）。
  一般化した処理の入力として、**どの区間にどの線路の規格（線形の規則）を当てるか**を与える。
- **必須の入力は駅の点だけで動くことが基本**（CLAUDE.md 作業のルール 6）。付け足しの情報はオプション。
- 入力ファイルは**疎結合**：データ源（OuDia・FreeTrain のセーブ）から一般化した入力ファイルを作る道具と、入力ファイルを受け取って線形を作る
  計算の本体は別。計算の本体はデータ源を知らない。
- 入力はできるだけストレスなく、簡単に、間違いなく、**スマホでできるインターフェース**で行う（作る仕事が待っている）。

## 2. 入力の手順（1 から線形を作るとき）
1. **駅の位置**：地図の上ですべての駅を打つ。
2. **駅のつながり**：駅を結ぶ線路の結節の関係（網の図。線形ではなく、つながり方だけ）。
3. **駅のどちら側につなぐか**：駅から 3 本以上の線が出る分岐駅では、分岐の角度の小さい方を分岐側と決めることはできないので、どちら側から
   出すかを人が決める。
4. **駅の属性**：棒線駅かそうでないか（オプション。`tables/station_yard.json`）。
5. **駅間ごとの線路の規格**：上の方（どんな高性能な列車が入るか。振子・高速なら曲線半径の規格が上がる）と、下の方（どんな低性能な列車が入るか。
   キハ40形・客車列車なら勾配を抑える）の 2 つの情報。指定の仕方は 2 通りで、**列車条件型を優先**（分類を分かりやすく整理できれば）：
   - 数値指定型：最急勾配と最小曲線半径をそれぞれ選ぶ。
   - 列車条件型：存在する列車を分かりやすい少数のグループに分け、そのグループが走る・走らないを指定して、間接的に曲線半径・勾配の使える範囲を決める。
6. **駅の情報**：駅名、線名、線区の割り当て。
7. **地上駅でない駅の指定**：地下駅など。
8. 「線を作ってください」。

## 3. 次の路線：沖縄の架空鉄道
- ある入力：FreeTrain のセーブ、OuDia のダイヤ。ない入力：GeoJSON（駅の位置）。
- 進め方（ユーザー）：① OuDia とセーブから一般化した入力ファイル（駅名・駅の情報・駅のつながり・系統）を作る道具を作る。② その入力ファイルを
  汎用のインターフェース（線形を作る環境）に入れ、**駅の位置だけが未指定**の状態から、地図の上で位置を落とし込む。③ GO。

## 5. 入力ファイルの形の案（2026-11-08、Claude の案。【未定】。ユーザーの判断を待つ）
1 路線網を 1 つのフォルダに置き、人が決めるものと、データ源から作るもの、計算が作るものを分ける。計算の本体（`build.py`）はこのフォルダだけを読む。
| ファイル | 中身 | 手順（2 節） | 必須か |
|---|---|---|---|
| `stations.json` | 停車場の一覧：id、名前、種類（駅・信号場・仮乗降場）、**位置（経度・緯度。未指定なら null）**、オプション：棒線駅、地下駅などの指定、駅の高さの例外 | 1・4・6・7 | 必須（位置は null でよい。計算は位置がそろってから） |
| `links.json` | 停車場のつながり：両端の停車場 id、**各端で停車場のどちら側につくか（`end: A|B`）**、線路の規格の id、単線・複線、電化 | 2・3・5 | 必須 |
| `standards.json` | 線路の規格の表：規格 id → 最小曲線半径・最急勾配・緩和曲線の決め方・最高速度・構内の決め方（列車条件型ならグループの組から表で引く） | 5 | 必須（既定の表を同梱） |
| `train_groups.json` | 列車のグループの表（6 節）と、車両 → グループの対応 | 5 | 列車条件型のとき |
| `systems.json` | 運転系統：名前、車両、通る停車場の並び（停車・通過） | ― | 走行曲線の計算に |
| `lines.json` | 線名・線区（書き出しと表示のため。停車場 id の並び） | 6 | 書き出しに |
- 停車場の「どちら側」：停車場ごとに A 側・B 側の 2 つの端を持つ。端から出る link が 2 本以上なら分岐器がある。単線の棒線駅は A・B に 1 本ずつ。
- 区間（いまの `sections.json` の行）は入力ではなく、計算が links から作る（幹線 → 支線の順位、端のつなぎ方、分岐の向き）。区間の切り方は人が決めない。
- 位置の入力は別の道具（スマホの地図のページ）が `stations.json` の位置だけを埋める。ほかは変えない。
- 今の `tables/sections.json`・`systems.json`・`station_yard.json` からこの形への変換は機械的にできる（択捉・国後で、変換 → 計算 → 今の結果と一致、で確かめる）。

## 6. 線路の規格：列車条件型の分類の案（【未定】）
今の系統の車両（12 種）を、線形に効く性能（最高速度・振子・勾配の登坂）で 5 つのグループに分ける案。規格は「上のグループ」（速さで曲線半径を決める）と
「下のグループ」（重さ・出力で勾配の上限を決める）の組で表す。
| グループ | 例（今の系統の車両） | 線形への要求 |
|---|---|---|
| S 高速振子 | キハ283系（130 km/h、振子） | 曲線半径は本則＋30 km/h で走れる大きさ。乙線以上 |
| A 高速（振子なし） | 789系1000番台、731系、キハ201系（120〜130 km/h） | 曲線半径は本則で 120〜130 km/h。乙線 |
| B 一般（電車・気動車） | 719系、キハ183系、キハ54形（100〜110 km/h） | 乙線・丙線 |
| C 普通の気動車 | キハ40形、キハ120形、キハ150形（85 km/h） | 丙線でよい。勾配 25‰ まで（単機） |
| D 機関車牽引（客車・貨物） | DD51形重連＋客車（95 km/h） | 勾配は 25‰（重連）、単機なら 15‰。乙線 |
- 駅間の規格の指定：「上 S・下 C」「上 B・下 D」のように 2 つを書く。規格の表（`standards.json`）が（上, 下）→ 最小半径・最急勾配・緩和曲線・構内 を与える。
  数値指定型は同じ表の値を直接書く形（`R_min`・`G_max`）で、両方を受け付ける。
- 今の入力との関係：`grade`（甲・乙・丙線）は「上」の、`GCAP`・`KYAKU25_ADD` は「下」の代わりをしていた。快速 白糠泊→東沸湖 の問題は「下 C（気動車）」の区間に 33.3‰ を当てたこと。
- 車両が規格に合うかの検査：系統の車両のグループが、通る全 link の（上, 下）の範囲にあるかを機械的に調べて表にする（合わなければ止まる）。
